## 4. 잘한 점 — 유지할 것

- **Nav2 ABORT를 성공으로 처리하던 결함 수정.** 이전 `NavigateToPoint`는 결과가 오기만 하면 SUCCESS였다. 실기에서 도착하지 못한 goal이 성공으로 넘어가는 경로를 막았다.
- **과거 이벤트 대신 "새 프레임"만 인정.** stream_id·frame_seq·촬영 시각으로 재전송·카메라 재시작·오래된 영상을 거른다. 하차 판단 근거로 적절한 설계다.
- **팔 완료는 실물 응답으로만.** `completion_basis=controller_position_response`이면서 `simulation_mode=false`일 때만 성공이다. 시간 경과를 완료로 보지 않는다.
- **정지 단계 주행 억제.** 팔 이동·층 대기 중 `nav_safety_gate`가 바퀴 명령을 막는다.
- **한계를 문서에 솔직히 적었다.** 카메라 숫자가 문 열림을 뜻하지 않는다는 점, 버튼 UI가 ROS 미션에 연결되지 않았다는 점, 실기 미검증을 명시했다.

- 마지막 확인 뒤 30 s(`hold_sec`) 안에 정면 자세 복귀와 하차를 모두 끝내야 한다. 하차 주행을 시작하기 전에 만료되면 다시 층수를 본다(`camera_behaviors.py:157-168`의 `_look()`). 하차 주행을 시작한 뒤 만료되면 `GuardedNavigate`가 goal을 취소하고 FAILURE를 낸다. 문이 늦게 열리거나 주행이 느리면 **문턱 위에서 멈춘 채 미션이 끝날 수 있다.**

- `_tick()`은 `_done` 검사보다 먼저 `/elevator/camera_state`를 발행한다. 360 s 실패 뒤에도 `looking=True`가 남아 새 프레임이 들어오면 다시 "확인"을 낼 수 있다. `SwitchFloor`에는 취소가 없다. 이미 전환 요청이 걸린 상태라면 미션이 멈춘 뒤 지도가 바뀔 수 있다(추정).
- 등급 판단: 실패 뒤에는 `mission_failed` 억제로 바퀴가 묶이므로 바로 충돌로 이어지지는 않는다. 그래서 🟠다. 그러나 복구할 때 위치 추정 상태가 예상과 달라진다.
- 수정: 미션 종료 뒤 층 확인 발행을 멈추고 전환 요청을 취소하는 경로를 둔다.

### CR-24 🔴 지도 전환이 초기 위치 반영을 확인하지 않고 끝난다

- 위치: [auto_floor_orchestrator_node.py:300-325](https://github.com/PackagU/Code_Space/blob/79fdcb215afc/test_workspace/elevator_auto_map_switch/src/auto_floor_orchestrator_pkg/auto_floor_orchestrator_pkg/auto_floor_orchestrator_node.py#L300-L325), [behaviors.py:347-353](https://github.com/PackagU/Code_Space/blob/79fdcb215afc/test_workspace/elevator_mission/src/elevator_mission_pkg/elevator_mission_pkg/behaviors.py#L347-L353)
- `_finalize()`는 `/initialpose` 발행을 시도한 뒤 결과와 관계없이 `ready`로 바꾼다. 지점이 설정에 없으면 발행을 건너뛰어도 `ready`다. 발행했더라도 AMCL이 받아 수렴했는지 보지 않는다. 미션은 이 `ready`만 보고 하차로 넘어간다.
- 영향: 다른 층 지도 위에서 틀린 위치로 문턱을 통과할 수 있다.
- 수정: 전환 완료 조건에 `initialpose_sent=true`와 AMCL 공분산·정합 기준을 넣는다(W11).

### CR-25 🟠 `fieldctl stop`은 미션이 보낸 goal을 취소하지 못할 수 있다

- 위치: [scripts/fieldctl:326-330](https://github.com/PackagU/Code_Space/blob/79fdcb215afc/scripts/fieldctl#L326-L330), [field_nav_cli.py:391-392, 420-423](https://github.com/PackagU/Code_Space/blob/79fdcb215afc/scripts/field_nav_cli.py#L391-L423)
- `fieldctl stop`은 게이트 정지를 건 뒤 `cancel`을 부르고 실패를 무시한다(`|| true`). `cancel`은 CLI가 저장한 goal ID 파일을 쓴다. 미션 노드는 이 파일을 쓰지 않는다. 그래서 바퀴는 멈추지만 미션의 Nav2 goal은 남을 수 있고, `fieldctl resume` 뒤 로봇이 다시 움직일 수 있다(추정).
- `field_nav_cli.py`에는 전체 취소(`--all`, 0 goal ID) 경로가 있다. 미션 중 정지 절차에 쓸 수 있는지 현장에서 확인한다.
- 등급 판단: 사람이 `resume`을 해야 움직이므로 🟠로 둔다. 런북에 반드시 적는다.

### CR-26 🟠 미션 프로세스가 죽어도 게이트는 주행을 막지 않는다

- 위치: [safety_gate.py:78-103](https://github.com/PackagU/Code_Space/blob/79fdcb215afc/src/drive_pkg/drive_pkg/safety_gate.py#L78-L103)
- 게이트는 scan·odom·drive ready·명령 신선도만 본다. 미션 실행기의 생존 신호(heartbeat)는 보지 않는다. 미션이 주행 중 죽으면 남은 Nav2 goal이 끝까지 달릴 수 있다(04 문서 F-C-14와 같은 문제).
- 등급 판단: 일반 Nav2 사용에서는 정상 동작이고, 게이트 소프트 정지가 있어 🟠로 둔다. 물리 비상정지는 ⚠️미확인이라 근거로 쓰지 않는다.
- 수정: 자율 미션 모드에서는 미션 heartbeat가 끊기면 게이트가 정지하도록 한다.

### CR-27 🟠 지도 전환 대기가 응답·실패·요청 구분을 하지 않는다

- 위치: [behaviors.py:320-323, 347-354](https://github.com/PackagU/Code_Space/blob/79fdcb215afc/test_workspace/elevator_mission/src/elevator_mission_pkg/elevator_mission_pkg/behaviors.py#L320-L354)
- 파라미터 설정 응답의 성공 여부를 보지 않는다. orchestrator가 `phase=failed`가 되면 `pending`이 true로 남아 `SwitchFloor`는 실패 대신 계속 RUNNING이다. 같은 층으로 다시 전환할 때는 이전 `ready` 상태를 새 완료로 오인할 수 있다(추정).
- 수정: 응답 결과 확인, `phase=failed` 즉시 실패, 요청별 식별자를 상태에 포함한다.

### CR-28 🟠 ★ 일반 주행 goal에 제한시간이 없다

- 위치: [behaviors.py:158-185](https://github.com/PackagU/Code_Space/blob/79fdcb215afc/test_workspace/elevator_mission/src/elevator_mission_pkg/elevator_mission_pkg/behaviors.py#L158-L185)
- `NavigateRoute`는 action 서버 발견, goal 응답, 결과를 무기한 기다린다. 미션 전체 제한시간도 없다.
- 현장 근거: 9/16 Nav2 로그에 `Failed to send goal response ... client will not receive response`가 실제로 남아 있다(`docs/presentation_20260916/navigation_events.txt` 13행). 응답이 유실되면 미션이 영원히 기다릴 수 있다.
- 수정: 단계별 제한시간과 goal 응답 유실 시 재전송(같은 goal 상태 확인 후)을 넣는다.

### CR-29 🟠 층수 브리지가 일부 HTTP 예외에서 죽는다

- 위치: [floor_reader_bridge.py:21-27](https://github.com/PackagU/Code_Space/blob/79fdcb215afc/test_workspace/elevator_mission/src/elevator_mission_pkg/elevator_mission_pkg/floor_reader_bridge.py#L21-L27), [elevator_camera_mission.launch.py:30-31](https://github.com/PackagU/Code_Space/blob/79fdcb215afc/test_workspace/elevator_mission/src/elevator_mission_pkg/launch/elevator_camera_mission.launch.py#L30-L31)

### CR-30 🟠 실제 팔 카메라 종류와 Docker 카메라 프로파일이 맞는지 모른다

### CR-31 🟡 "새 프레임" 기준이 촬영 시각·연속 프레임을 보장하지 않는다

- 수정: 촬영 직후 시각을 기록하고, 필요하면 연속 번호를 요구하거나 브리지 주기를 카메라 처리 주기보다 빠르게 한다.
