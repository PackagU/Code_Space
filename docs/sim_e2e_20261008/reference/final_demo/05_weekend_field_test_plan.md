# 주말 현장 시험 계획

작성일: 2026-10-07. 대상: 사용자가 말한 이번 주말 시험(2026-10-10~11로 해석, 실제 일정 ⚠️미확인). 상태: **계획만**. Codex 4회차 검토(명령 정확성·안전)를 반영했다.

## 0. 이번 주말의 목표

이번 주말에 완전 자율 왕복을 시도하지 않는다. 지금 코드에는 탑승 전 대기 없음(CR-01), 가상 좌표 기본값(CR-03), 상하차 mock(CR-04), 지도 전환 뒤 위치 확인 없음(CR-24)이 있어 실차 카메라 미션을 돌리면 위험하다.

이번 주말 목표는 마일스톤 **M0**이다.

1. 이성덕 코드 중 실물로 확인할 수 있는 부분(팔 카메라 자세, 층수 인식)을 확인한다.
2. 남은 기능을 설계하는 데 필요한 현장 값(엘리베이터·버튼·표시창·문턱·택배 칸·문 상태별 LiDAR)을 잰다.
3. Nav2 실패 구간(보관함, F2 엘리베이터 앞)을 반복 시험한다.

원칙:

- 로봇 주행·팔·지게팔 동작은 현장에서 따로 승인한 뒤 실행한다([AGENTS.md](../../AGENTS.md) 작업 경계).
- 물리 비상정지 담당 1명을 둔다. 프로그램 정지 버튼은 물리 비상정지를 대체하지 않는다. 물리 비상정지가 바퀴·팔·지게팔 중 무엇을 멈추는지 먼저 확인한다.
- [04 문서 안전 관문](04_failure_modes.md) 가운데 이번 주말에 넣은 것은 팔 경로 간섭 확인(T2 0단계)과 지게팔 무부하 정지 시험(T7a)뿐이다. 하중을 실은 정지·전원 차단 유지(F-C-25)와 후진·회전 사각 검증(F-C-26)은 이번 주말 범위 밖이며, 무인 시험 전에 따로 통과해야 하는 관문으로 남는다.
- 기록하지 않은 시험은 하지 않은 것으로 본다. 6절 양식으로 남긴다. 사람이 도운 결과는 M0 측정값일 뿐 완전 자율 성공이 아니다.
- 아래 명령 가운데 9/16 가이드에 없는 것은 **초안**이다. 현장에서 실제 출력으로 확인한 뒤 쓴다.
- 코드 반영·컨테이너 재생성 뒤에는 T0를 처음부터 다시 한다.

### T2 팔 카메라 자세 확인 — 이성덕 코드의 핵심 실물 확인

목적: `front_view`·`floor_view`가 안전하고, 카메라가 원하는 대상을 보는지 확인한다. LiDAR 가림과 PRAD 응답 의미도 함께 본다.

전제: 차체 정지(`/nav_safety/stopped=true`), 팔 주변 사람 없음, `/dev/arm_servo`를 쓰는 다른 프로그램 없음.

**0단계 — 간섭 확인.** HOME·`front_view`·`floor_view`의 PWM 범위(900~2600 공통)는 실물 안전 범위가 아니다(CR-19). 팔 전원을 끈 상태에서 세 자세 사이 이동 경로가 차체·LiDAR·케이블에 닿지 않는지 눈으로 본다. 첫 동작은 정지 담당이 비상정지에 손을 둔 상태에서 1회만 하고, 이상이 없을 때 반복한다.

**장치 전달 확인(컨테이너 안에서 할 때).** 9/10 기록 기준 compose 장치 기본값은 `/dev/null`이다. `/dev/null`도 문자 장치이므로 "문자 장치인지"만으로는 판정할 수 없다. 장치 번호를 비교한다.

```bash
docker exec ros2_humble stat -Lc '%n %t:%T' /dev/arm_servo /dev/null
stat -Lc '%n %t:%T' /dev/arm_servo
```

컨테이너 안 `/dev/arm_servo`가 `/dev/null`(1:3)과 다르고 호스트 `/dev/arm_servo`와 같아야 한다. `.env`의 `ARM_SERVO_DEVICE`를 바꿔 컨테이너를 다시 만들 때는 T1 4번을 따른다. 이번 주말에 컨테이너를 다시 만들지 않으려면 아래 호스트 스크립트로 같은 PWM 자세를 보내 확인한다.

명령 초안(컨테이너 안, `robot_arm_pkg` 빌드 후):

```bash
ros2 launch robot_arm_pkg arm_sequence.launch.py serial_port:=/dev/arm_servo
```

launch 기본값은 `home_on_start=false`, `simulation_mode=false`, `self_test=false`, `require_homed=true`, baud 115200이다. 노드를 켜기만 해서는 팔 명령을 보내지 않는다. 첫 `home` 명령에서 팔이 2000 ms 동안 HOME 자세로 움직인다.

다른 창에서 상태를 보고 명령을 하나씩 보낸다. request_id는 매번 새 값이어야 한다. 같은 값은 거부되며, 거부된 ID도 다시 쓰지 않는다.

```bash
ros2 topic echo /packagu_arm/status
ros2 topic pub --once /packagu_arm/command std_msgs/msg/String "{data: '{\"request_id\": \"t2-home-01\", \"action\": \"home\"}'}"
ros2 topic pub --once /packagu_arm/command std_msgs/msg/String "{data: '{\"request_id\": \"t2-front-01\", \"action\": \"view\", \"view\": \"front_view\"}'}"
ros2 topic pub --once /packagu_arm/command std_msgs/msg/String "{data: '{\"request_id\": \"t2-floor-01\", \"action\": \"view\", \"view\": \"floor_view\"}'}"
```

`view`는 home 응답이 일치한 뒤에만 받는다(`require_homed`). 이 명령을 쓸 수 없으면 버튼 앱의 이동 기능으로 같은 PWM에 맞춘다. 버튼 앱은 실제 모드(`--execute --field-approved`)로 켜면 카메라를 켜기 전에 위치를 읽고 **Enter 뒤 3초 동안 home으로 움직인다**. 이 Enter를 별도 동작 단계로 다루고, 주변·HOME 경로·정지 담당을 확인한 뒤 누른다.

| 측정 | 방법 | 기록 |
|---|---|---|
| 카메라 종류 | 팔에 달린 카메라가 USB 웹캠인지 CSI(IMX219)인지, `ls /dev/v4l/by-id/`·`ls /dev/video*` | 장치 경로 (CR-30) |
| 컨트롤러 응답 일치 | 상태 `completed`와 `measured_pwm` | 자세별 PWM. 이것은 "컨트롤러 응답이 목표와 같다"는 뜻이며 물리 도달 증거가 아니다 |
| 물리 도달 | 자세별 사진·영상, 기준점 각도 측정 | 응답 일치와 따로 기록 |
| PRAD 의미 | 아래 초안 스크립트로 긴 이동(5000 ms) 도중 PRAD를 반복해서 읽고 같은 시간의 영상과 비교 | 곧바로 목표값이면 echo 가능성이 높다. 중간값이 나와도 컨트롤러 내부 보간값일 수 있어(추정) 영상과 맞을 때만 실제 위치에 가깝다고 본다 |
| 카메라 화면 | 자세별 사진 저장 | 무엇이 보이는지 |
| LiDAR 가림 | 자세별 `/scan`을 RViz로 비교 | 가림 각도 범위 |
| 이동 중 충돌 | 관찰 | 차체·LiDAR·카메라 케이블 간섭 |
| 반복 정밀도 | 같은 자세 5회 반복, 화면 기준점 픽셀 위치 | 픽셀 편차 |

PRAD 의미 확인 초안. 팔이 home에 있을 때 실행한다. 팔 노드와 버튼 앱을 모두 끈 뒤 Jetson 호스트에서 실행한다(포트 단독 사용). 실제 팔이 움직이므로 현장 승인 뒤에만 한다. 이 스크립트는 팔 노드의 home 검사·취소 처리를 거치지 않으므로, 예외나 Ctrl+C가 나면 정지 명령(`PDPT`)을 보내고 포트를 닫도록 했다. 오류 뒤 자동으로 home에 보내지 않는다. 읽기 한 번에 네 관절을 차례로 조회하므로 간격은 0.5 s보다 길다. 조회 전후 시각을 함께 기록한다. 호스트 Python 3.8·pyserial에서 동작하는지는 ⚠️미확인이다.

```bash
cd ~/Code_Space/src/robot_arm_pkg
python3 - <<'EOF'
import time
from robot_arm_pkg import servo_protocol as sp
front = {"front_view": {"000": 1500, "001": 1500, "002": 2000, "003": 1500}}
driver = sp.SerialPoseDriver("/dev/arm_servo")
try:
    print("before", driver.read_positions())
    driver.send_pose("front_view", 5000, front)
    for _ in range(12):
        time.sleep(0.5)
        t0 = time.monotonic()
        positions = driver.read_positions()
        print(round(t0, 3), round(time.monotonic(), 3), positions)
except BaseException as exc:
    print("stop:", repr(exc))
    driver.stop_all()
    raise
finally:
    driver.close()
EOF
```

끝나면 팔을 home으로 되돌린 뒤 다음 시험으로 넘어간다.

### T3 엘리베이터 측정 — F1·F2 각각

목적: 문·버튼·표시창 관련 설계 값 확보(W07~W10). 로봇이 탈 필요는 없는 측정이 대부분이다. 캐빈 안에서 하는 측정은 시설 담당과 정한 절차를 따르고, 손·몸으로 문을 막지 않는다.

| 항목 | 측정 | 반복 |
|---|---|---|
| 호출 후 문 열림 유지 | 호출 후 문 완전 열림 → 닫힘 시작(실제로 쓸 수 있는 시간) | 3회 |
| 도착 후 문 열림 유지 | 운행 도착 시 완전 열림 → 닫힘 시작 | 3회 |
| 표시 변화 → 문 열림 | 표시창이 목표층으로 바뀐 시각 → 문 열림 시작 | 3회 |
| 문 폭·문턱 | 열린 폭, 틈 폭, 단차 높이. **두 층 모두 1일차에 잰다**(T9 모형 제작용) | 1회 |
| 캐빈 안 치수 | 폭 × 깊이, 패널 위치(문에서 거리), 버튼별 중심 높이 | 1회 |
| 버튼 형식 | 기계식·터치식, 캡 모양·색, 숫자 형식(인쇄·양각·점자), 비상 버튼 위치 | 사진 |
| 승강장 버튼 | 높이, 문틀에서 거리, ▲▼ 배치 | 사진 |
| 표시창 | 승강장·캐빈 각각 존재 여부, 높이, 숫자 크기, 방식(LED 세그먼트·도트·LCD) | 사진·영상 |
| 운영 | 호기 수, 운행 층, 시간대별 제한·카드 인증, 운행 방향 표시 | 기록 |
| 출입문 | 앞뒤 관통형 여부, 층마다 열리는 문 방향 | 기록 |
| 통신 | 캐빈 안 Wi-Fi(ping 손실) | 1회 |

**T3-L 문 상태별 LiDAR 기록(D5 근거).** base를 켜고 로봇을 문 앞에 정지시킨 채 `/scan`을 rosbag으로 기록하고, 같은 시간에 문을 휴대폰으로 촬영한다. 닫힘·반쯤 열림·완전 열림을 모두 담는다. 가능하면 사람이 문 앞에 선 상태와 팔이 앞을 가린 상태도 기록한다. 닫히는 문에 로봇을 일부러 끼우는 시험은 하지 않는다.

로봇 카메라로 찍을 후보 위치: 호출 버튼 관측 위치, 승강장 표시창 관측 위치, 캐빈 패널 위치, 캐빈 문 방향 위치. 위치마다 `front_view`·`floor_view` 사진을 남긴다.

### T4 층수 인식 실측

목적: 실제 표시창에서 `floor_reader`가 동작하는지 본다(W08). 이성덕 커밋의 새 프레임 필드(`/api/state`의 `frame_seq`·`stream_id`)를 확인한다.

1. 팔을 `floor_view`로 두고 표시창이 화면에 들어오게 로봇을 세운다.
2. 버튼 앱을 끈 상태에서(카메라 단독 사용) `tools/floor_reader/app.py`(T1에서 반영한 경우)를 USB 웹캠으로 실행한다.

   ```bash
   cd ~/Code_Space/tools/floor_reader
   python3 app.py --source /dev/v4l/by-id/usb-Generic_USB2.0_PC_CAMERA-video-index0
   ```

   노트북에서 `ssh -N -L 8765:127.0.0.1:8765 hsm@<Jetson 주소>`로 터널을 열고 브라우저에서 `http://127.0.0.1:8765`를 연다. 카메라 by-id 경로는 9/15 기록값이다. 실제 장치 이름은 `ls /dev/v4l/by-id/`로 먼저 확인한다.
3. 화면에서 ROI를 지정하고 실제 숫자(1·2, 가능하면 B1)를 등록한다. 이 앱은 ROI가 하나뿐이고 같은 숫자를 다시 등록하면 기존 템플릿을 덮어쓴다(`app.py:260, 272-273`). 장소(F1 승강장, F2 승강장, 캐빈)마다 등록을 마치면 `data/` 폴더를 장소 이름으로 따로 복사해 둔다.
4. 판정할 목표층을 `/target`으로 적용한다. 기본 목표는 `4`다(`app.py:97`). 프레임별 `floor` 판정과 안정된 목표층 이벤트를 구분해 기록한다.
5. 엘리베이터 운행을 지켜보며 `/api/state`의 `floor`·`score`·`margin`·`frame_seq`·`stream_id`·`updated`·`error`를 기록하고, 같은 장면을 휴대폰으로 찍어 시각을 맞춘다.

| 목표층 표시 후 판정 지연 | 3 s 이하 |
| 다른 층을 목표층으로 판정 | 0회 |
| UNKNOWN 빈도 | 기록 |
| 표시창이 ROI 밖으로 나가는 정차 오차 | 몇 cm·몇 도부터인지 기록 |

### T5 버튼 인식 영상

목적: 기존 인식기 전제("어두운 판 위 흰 원형 캡")가 실제 버튼에 맞는지 확인한다(D4).

1. 버튼 앱을 **미리보기 모드**(팔 포트를 열지 않음)로 실행한다. 9/16 현장에서 쓴 배포본 위치는 `~/button_arm_test_20260915`다. `~/Code_Space/tools/button_arm_test`를 쓰면 어느 쪽을 썼는지 기록한다.

   ```bash
   cd ~/button_arm_test_20260915
   python3 -B app.py --source /dev/v4l/by-id/usb-Generic_USB2.0_PC_CAMERA-video-index0
   ```

   노트북에서 `ssh -N -L 8091:127.0.0.1:8091 hsm@<Jetson 주소>`로 터널을 열고 `http://127.0.0.1:8091`을 연다. 층수 앱(8765)과 동시에 켜지 않는다.
2. 승강장 ▲▼ 버튼과 캐빈 패널을 화면에 넣고 검출 결과를 기록한다. 프레임을 저장해 둔다.
3. 검출되고 안전 관문(T2 0단계, 비상정지 범위)을 통과했을 때만 현장 승인 뒤 실제 모드로 전환한다. 전환 시 Enter 뒤 home 이동이 있다(T2 참고).
   - ▲·▼는 일반 보정점이 아니라 `현재 자세 → ▲/▼ 저장`으로 따로 저장해야 쓰인다.
   - "1"은 화면 위치와 무관하게 메뉴 6 고정 자세로 누른다. 일반 보정점을 추가해도 "1"의 자세는 바뀌지 않는다.
   - "2"는 앱의 누르기 목표로 고를 수 없다(캐빈 규칙이 올라감 = 4, 내려감 = 1로 고정, `app.py:27-30`). "2"는 영상·교시 데이터 수집까지만 한다.
   - 비상호출·정지 버튼은 접근·후퇴 경로까지 금지 영역으로 보고 교시하지 않는다.
   - 누르기 전후 점등 상태와, 이미 켜져 있던 경우를 기록한다.

### T6 Nav2 반복

목적: 9/16 실패 구간의 재현과 원인 수집(W02).

시작 전에 [08 데스크톱 Gazebo 자체 시험](08_desktop_gazebo_selftest_plan.md) G1·G2·G4 결과를 본다. 시뮬 결과는 현장 판정을 대신하지 않는다.

시작 전: 팔을 수납하고 ROS 팔 노드를 끈다. 팔·지게팔 노드가 있으면 Nav2 시작 스크립트가 거부한다(`start_field_navigation.sh:63`).

| 구간 | 반복 | 기록 |
|---|---|---|
| F1 출발 표식 → `f1_locker` | 5회 | 결과, 시간, 정차 위치 오차(줄자), bag |
| F2 `f2_delivery_left_room4` → `f2_elevator_staging_v1` | 5회 | 결과, collision-ahead 수, bag, 엘리베이터 앞 정차 위치 퍼짐 |

- 엘리베이터 앞 정차 퍼짐은 F2 staging 5회에서 함께 잰다(따로 세지 않는다). F1 엘리베이터 앞은 시간이 남으면 추가한다.
- goal 하나당 제한 시간 300 s `[제안값]`를 두고, 넘으면 사람이 정지·취소한다. CLI의 goal 대기 자체에는 제한 시간이 없다(`field_nav_cli.py:395-397`).
- 모든 goal 전에 9/16 가이드의 `record check`·`pose capture`를 따른다.
- CPU: `./scripts/fieldctl diagnose`는 순간값만 준다. 평균·최대는 시험 동안 따로 연속 기록한다(예: `docker stats`를 일정 간격으로 파일에 저장).
- 정지·재개 순서: `fieldctl stop`으로 게이트 정지를 유지한 채, 필요하면 `./scripts/fieldctl cancel --all`(전체 취소, 코드에 있는 옵션)로 남은 goal을 취소한다. 취소 응답은 정지 완료가 아니므로 action 최종 상태와 실제 정지를 확인한 뒤에만 `resume`한다. 확인되지 않으면 게이트를 유지하고 Nav2를 끈다(CR-25).

### T7 지게팔 시험

목적: 정지 기능, 탈조·위치 오차, 시간 측정(W05). 손·발을 포크 아래에 두지 않는다.

**T7a 무부하(1일차, 하중 시험보다 먼저).**

1. 방향 확인: `u`·`d` 각 1회. 터미널 명령은 입력 뒤 **Enter**를 눌러야 전송된다(`lift_uno_position_terminal.py:87-96`).
2. 정지 확인: 움직이는 중 `!` + Enter. 전송부터 실제 정지까지 지연을 잰다. 물리 비상정지가 지게팔을 멈추는지도 확인한다.
3. 복구: 정지 뒤에는 위치 기준이 사라진다(9/16 가이드). 포크가 **눈으로 보아 완전히 아래 끝이면 `b`, 위 끝이면 `t`**로만 기준을 다시 잡는다. 중간이면 시험을 멈추고 사람이 안전하게 복구한다. 중간 위치를 끝으로 선언하지 않는다.

**T7b 하중(2일차).** 시연 택배를 올린 상태로 `u`·`d` 각 3회. 펄스 완료 시점과 실제 끝 위치를 비교하고 소요 시간을 잰다. 걸림·이상 소리가 나면 즉시 정지한다.

### T8 택배 칸 영상·치수

목적: 칸 인식 방식 선택용 영상(D3, W04)과 칸 치수(D12).

1. `f1_locker` 관측 위치에서 `front_view` 사진을 찍는다.
2. 칸 1·2·3에 택배를 각각 놓고 5장씩, 빈 상태 5장, 2개 놓은 상태 2장.
3. 정차 위치·각도를 조금씩 바꾼 사진도 칸별로 2장씩 찍는다(정차 오차 영향).
4. 칸 배치(가로·세로)와 칸별 바닥 높이·폭·깊이, 포크가 들어갈 간극을 줄자로 잰다(D12, W05 칸별 수치).
5. 가능하면 다른 시간대(조명)에 한 번 더 찍는다.

### T9 문턱·보조 바퀴

[9/15 개선 절차 6절](../../docs/bringup_guide/2026-09-15_autonomy_field_procedure.md)을 따른다. T3에서 두 층의 문턱 치수를 먼저 확보한다. 보조 바퀴 H0 지상고를 재고, 실측 치수에 맞춘 모형 문턱에서 0.03 → 0.05 → 0.08 → 0.10 m/s(9/15 절차의 `[제안값]`) 순으로 수동 저속 시험한다. 걸리면 그 속도에서 가속을 반복하지 않는다. 실제 문턱 탑승은 모형 통과 뒤에만 하고, 택배를 실은 시험은 하중 안정성(T7b) 확인 뒤에 따로 한다. 주행 명령 발행자는 하나만 둔다(게이트는 장애물 거리를 보지 않는다).

### 하지 않는 것

- `elevator_camera_mission.launch.py` 실행. 가상 좌표·가상 지도 기본값(CR-03)과 탑승 전 대기 없음(CR-01) 때문이다.
- `2026-10-06` 브랜치 `nav2_params.yaml`로 덮어쓰기. 이 파일은 9/17에 철회하기로 한 wall_push 상태다(D6).
- 사람 없이 엘리베이터 탑승 시도.
- 닫히는 문에 로봇을 일부러 끼우는 시험.
