## 2. 작업 목록

우선순위: **P0** 주말 시험 전(10/7~10/9) · **P1** 주말 시험 중 측정·확인 · **P2** 주말 뒤 구현 · **P3** 통합 뒤 다듬기.

### W01 실측 설정 연결과 fail-closed — P0 (설정), P2 (코드)

- 내용: 미션 패키지가 가상 좌표(`kku_nav_points.yaml`)·가상 지도(`floor_maps.yaml`) 대신 실측 지도(`map_pins.json` 고정본)와 실측 지점을 쓰게 한다. 01 문서 4절 지점 목록을 미션 설정 파일 하나로 모은다.
- 완료 기준: 카메라·실기 모드 launch가 설정 경로를 명시하지 않거나 고정본과 다른 지도를 가리키면 시작을 거부한다(오프라인 시험). 모든 지점이 현장 캡처값이다.
- 관련: CR-03, CR-13, CR-21. 영역: 통합·SLAM.

### W02 Nav2 기본값 정리와 핵심 구간 신뢰도 — P0 (결정), P1 (시험)

- 내용: 사용자가 9/17에 결정한 wall_push_v1 철회를 Jetson과 브랜치에 반영하고 확인한다(CR-11, D6). 9/16 실패 구간 `f1_locker`, `f2_elevator_staging_v1`의 원인을 bag·로그로 분석하고 반복 시험한다. 9/16 로그에 costmap clear 서비스 시간 초과가 반복됐으므로 CPU 부하도 함께 본다.
- 완료 기준: 두 구간 각 5회 중 5회 도착 `[제안값]`. 실패하면 원인과 다음 조치를 기록한다.
- 영역: SLAM·Nav.

### W03 카메라 서비스 — P2

- 내용: 팔 카메라를 단독으로 여는 서비스 하나를 둔다. 모드(택배 칸·버튼·층수)를 바꿔 가며 결과를 낸다. 결과마다 stream_id·frame_seq·촬영 시각을 붙인다. 프레임이 끊기면 재연결한다(CR-09, CR-10). 장치는 `/dev/v4l/by-id/...` 고정 경로를 쓴다. 실제 팔 카메라가 USB인지 CSI인지 먼저 확인한다(CR-30). 결과 전달 경로가 예외로 죽지 않게 한다(CR-29).
- 결과 계약: 결과마다 장소·인식 모드·관측 요청 ID도 붙인다. 모드·팔 자세·로봇 방향·스트림이 바뀌면 누적 확인을 초기화하고, 해당 관측 요청 이후의 안정된 프레임만 인정한다. 모드 변경 직전 결과를 새 장소 판단에 쓰지 않기 위해서다.
- 가장 작은 구현 후보: 새 서비스를 따로 만들기보다 기존 영상 소유 프로세스(`floor_reader` 또는 버튼 앱)를 넓혀 인식 함수만 바꿔 쓰는 방법. 한 프로세스가 죽으면 모든 비전이 멈추므로 상태 감시를 같이 둔다.
- 완료 기준: 모드 전환 1 s 이내 `[제안값]`. USB 재연결 뒤 자동 복구와 stream_id 변경을 시험한다. 미션 중 CPU 사용률을 측정한다.
- 영역: 비전.

### W04 택배 칸 인식 — P1 (영상 수집), P2 (구현)

- 내용: 보관함 관측 위치에서 `front_view`로 칸 1·2·3 중 택배가 있는 칸을 판정한다. 방식 후보: ① 칸 또는 택배에 표식(ArUco 등) ② 택배 색·면적 ③ 빈 보관함 기준 영상과의 차이. ArUco는 컨테이너 OpenCV의 `cv2.aruco` 포함 여부가 ⚠️미확인이다.
- 칸 배치 확인: 세 칸이 가로로 놓였는지 세로(높이가 다름)로 놓였는지 먼저 잰다. 높이가 다르면 지게팔이 위·아래 끝 말고 중간 높이로도 가야 한다(D12).
- 완료 기준: 칸별 20회 판정 중 오판 0 `[제안값]`. 조명·정차 오차 조건을 바꿔도 같은 결과여야 한다. 판정 불가 시 "모름"을 내고 미션을 멈춘다.
- 영역: 비전.

### W05 지게팔 ROS 노드와 원점 — P1 (측정), P2 (구현)

- 내용: 지게팔 시리얼을 미션 내내 열어 두는 노드를 만든다. Uno는 USB를 열 때 리셋되어 위치 기준이 사라진다. 명령은 상승·하강·정지·상태이고, 완료 판정은 펌웨어 `UP complete`·`DOWN complete`와 `position_pulses`다.
- 하드웨어 결정: 아래 끝 리미트 스위치를 추가해 자동 원점을 만들지, "시작 전 기준 설정"을 준비 단계로 둘지 정한다(4절 D2).
- 적재 확인: 카메라 또는 포크 위 스위치로 택배가 실렸는지 확인한다. 현재는 수단이 없다.
- 위치 기준 규칙: 노드가 포트를 연 뒤 원점 준비를 하고 나서야 명령을 받는다. Uno 리셋·통신 단절이 생기면 위치를 "미확인"으로 바꾸고, 기준을 임의로 다시 잡거나 자동 재개하지 않는다.
- 칸별 수치: 칸마다 포크 진입 높이·간극·삽입 깊이를 잰다(W04 칸 배치와 함께).
- 완료 기준: 택배를 실은 상승·하강 각 5회 `[제안값]`, 펄스 완료와 실제 끝 위치가 일치한다. 정지 명령 지연의 상한을 측정값으로 정해 합격 경계로 둔다. 끝 위치의 물리 확인 방법(리미트 스위치·영상)을 정한다.
- 영역: 리프트·HW.

### W06 미세 동작 모듈 — P2

- 내용: 저속 직진·후진·제자리 회전을 odom으로 수행한다. IMU는 9/12 기준 데이터가 발행되지 않았다(일반 펌웨어 minimal 피드백). IMU를 쓰려면 IMU 변형 펌웨어의 데이터·축·부호 검증이 먼저다. 움직이는 방향의 LiDAR 최소 거리로 정지한다(아래 장애물 확인 범위). 보관함 접근, 하역 정렬, 버튼 앞 정렬, 캐빈 안 회전에 쓴다.
- 먼저 기존 Nav2 behavior(`drive_on_heading`·`backup`·`spin`, 현재 `nav2_params.yaml` behavior_server에 설정됨)로 실제 접근 거리를 시험한다. 이 behavior는 costmap 충돌 검사를 하므로 보관함·택배로 다가가는 동작을 거부할 수 있다(추정). 부족한 구간만 별도 모듈로 만든다. 포크 삽입은 "다가갈 대상"과 "피할 장애물"을 구분하는 별도 판단이 필요하다.
- `/cmd_vel` 소유: Nav2가 goal을 실행하지 않을 때만 발행한다. `nav_safety_gate`를 우회하지 않는다. velocity_smoother 출력과 겹치지 않는지 확인한다.
- 장애물 확인 범위: 전방만이 아니라 움직이는 방향 전체를 본다. 후진할 때는 뒤쪽, 회전할 때는 차체·포크·택배가 쓸고 지나가는 원 전체다. `nav_safety_gate`는 신선도·속도·억제만 보고 장애물 거리는 보지 않는다(`safety_gate.py:78-103`).
- 완료 기준: 직진 0.30 m 명령의 실제 이동 오차 ±2 cm, 후진 오차 ±2 cm, 90° 회전 오차 ±3° `[제안값]`. 각 10회. 장애물 정지거리와 택배 적재 상태 회전도 잰다.
- 영역: 주행·통합.

### W07 카메라 기반 버튼 누르기 ROS 연동 — P1 (영상·보정점), P2 (구현)

- 내용: `tools/button_arm_test`의 `vision.py`(검출·▲▼·숫자)와 `calib.py`(픽셀→PWM)를 미션에서 쓰게 옮긴다. 팔 노드에 계산된 자세를 받는 `press_pose` 명령을 추가한다. 접근 자세 오프셋(001 −300, 002 +100)과 안전 범위 검사를 유지한다.
- 보정점: 승강장 F1(▲·▼), 승강장 F2(▲·▼), 캐빈 패널(1·2, 필요하면 열림)을 장소별로 따로 둔다. 기존 보정점은 메뉴 6·7 자세 2개와 화살표 자세뿐이다.
- 첫 구현 권장안: 범용 픽셀→PWM 변환보다, 필요한 버튼(▲·▼·목적층·"1")만 장소별로 교시하고 카메라로 대상과 관측 위치가 교시 때와 같은지 확인한 뒤 누르는 방식이 단순하다. 관측 자세·거리·차체 방향이 허용 범위 밖이면 미세정렬하거나 누르기를 거부한다. `calib.py` 보간은 대상 거리·교시 영역이 같다는 전제다.
- 안전: 누를 수 있는 버튼 허용 목록을 둔다. 비상호출·정지 버튼 주변을 금지 영역으로 정한다(04 문서 F-S8-03). 접근 → 누름 → 후퇴 경로가 금지 영역을 지나지 않는지 검사한다.
- 눌림 확인: 누르기 전 점등 상태를 저장하고 전후 밝기 변화로 판정한다. 다른 사람이 이미 켠 버튼, 호출 직후 바로 꺼지는 버튼(문이 바로 열림)을 따로 처리한다. 누름 응답과 호출·층 선택 성공을 구분한다. 확인 실패 시 다시 인식하고 1회만 재시도한다.
- 전제 확인: 인식기는 "어두운 판 위 흰 원형 캡"을 찾는다(`vision.py:13-43`). 실제 엘리베이터 버튼이 금속·조명 링·점자형이면 검출이 안 될 수 있다. 터치식 버튼이면 고무 팁으로 눌리지 않는다. 주말에 실제 버튼 사진과 형식을 먼저 확인한다(D4).
- 완료 기준: 장소별 목표 버튼 10회 누르기 중 10회 점등 `[제안값]`, 오버튼 0회.
- 관련: CR-02. 영역: 팔·비전.

### W08 층수 인식 현장화 — P1 (등록·측정), P2 (구현)

- 내용: 승강장 F1·F2와 캐빈 표시창마다 ROI 프로파일을 둔다(CR-08). 실제 숫자를 카메라로 등록한다. 정차 오차로 표시창이 벗어나면 회전 미세정렬로 표시창을 화면 중앙에 맞춘다.
- 측정할 것: 관측 거리, 숫자 높이(화면 픽셀), LED 깜빡임에 의한 줄무늬, 반사, 표시가 바뀐 뒤 문이 열리기까지의 시간.
- 완료 기준: 장소별로 층이 바뀌는 장면 연속 관측에서 오판 0, 목표층 확인 지연 3 s 이하 `[제안값]`. 촬영 시각 기록과 연속 프레임 기준을 정한다(CR-31).
- 영역: 비전.

### W09 LiDAR 문 열림 감지 — P1 (scan 수집), P2 (구현)

- 내용: 로봇 앞 문 방향 각도 구간의 거리로 열림·닫힘을 판정한다. 열리면 문 평면 너머 캐빈 벽(또는 복도)까지 거리가 길어진다. 결과는 `/elevator/door_state`(기존 선택형 문 모드 형식)로 발행해 `require_door_confirmation:=true`를 쓴다.
- 필드별 근거: 기존 게이트(`elevator_camera.py` `observe_door()`)는 `source=sensor`, 새 `stamp`, `door_state=open`, `stopped=true`, `exit_clear=true`를 모두 요구한다. 각 필드를 다음처럼 정한다. 상수 `true`로 채우지 않는다.
  - `door_state`: 문 구간 거리 판정.
  - `stopped`: 문이 열린 상태가 일정 시간 유지되면 정지로 본다. 엘리베이터는 정지·착상 뒤에만 문이 열린다는 설비 동작에 기댄 가정이다(검증 대상).
  - `exit_clear`: 진행 경로 폭의 LiDAR 빈 공간. 2D LiDAR 평면 밖(낮은 물체 등)은 확인하지 못한다고 기록한다.
  - 판정 불가(무효 거리, 팔·사람 가림, 센서 단절)는 `unknown`으로 내고 열림으로 보지 않는다.
- 캐빈 안 사람·물체로 통과 공간이 막히면 탑승하지 않는다.
- 측정할 것: 문 닫힘·반열림·완전열림의 scan 구간 거리, 문이 열린 채 유지되는 시간(dwell time).
- 완료 기준: 열림·닫힘 판정 지연 0.5 s 이하, 20회 오판 0 `[제안값]`.
- 영역: SLAM·통합.

### W10 엘리베이터 탑승·하차·캐빈 안 이동 — P1 (치수·문턱), P2 (구현)

- 내용: 문 통과(저속 직진, 문틀 중앙 유지), 캐빈 패널 위치 정렬, 문 방향 회전, 하차를 미세 동작 모듈과 Nav2 조합으로 만든다. 캐빈 안처럼 좁은 곳에서는 전역 경로 계획과 recovery(spin·backup)가 위험할 수 있다.
- 문턱 구간 정책: 문턱 전·횡단 중·완전 이탈 세 구간을 나눈다. 횡단 중 문이 닫히기 시작하면 정지할지 통과를 마칠지 정한다(D7). 통과 공간이 막힌 경우와 비상정지가 항상 우선이다. 문 열림 유지 시간 예산에는 인식 시간·팔 접기·출발 지연·이동 시간을 모두 넣고, 로봇 속도(0.10 m/s 근처)와 비교해 결정한다.
- 하드웨어: 9/15 보조 바퀴 장착 후 탑승 실패 보고가 있다. 2 mm 하향 뒤 재시험은 ⚠️미확인이다(W14).
- 완료 기준: F1·F2 각 탑승·하차 5회 성공, 문 접촉 0 `[제안값]`.
- 영역: 주행·통합.

### W11 층 지도 전환 현장화 — P2

- 내용: `floor_maps.yaml`을 실측 지도(고정본)로 바꾼다. 캐빈 안 현재 자세를 다음 층 지도 좌표로 옮겨 초기 위치로 보낸다(01 문서 4절, 정확도 개선은 미검증 제안). 전환 뒤 `/initialpose` 반영은 반드시 확인한다(CR-24). 위치 정합(AMCL 수렴) 확인의 시점·방식은 아래 두 방식 중 시험으로 정한다(미결정). 전환 실패·요청 구분을 고친다(CR-27). 문이 닫힌 캐빈 안에서는 scan 특징이 적어 AMCL이 흔들릴 수 있다.
- 주의: AMCL은 이동량 기준(`update_min_d: 0.25`, `update_min_a: 0.2`)을 넘어야 필터를 갱신한다. 캐빈 안에 서서 기다리기만 해서는 수렴이 진행되지 않을 수 있다. 두 방식을 비교한다. ① 문이 열린 뒤 AMCL 무이동 갱신 요청(Humble AMCL `request_nomotion_update` 서비스, 현장 확인 필요)으로 정합 확인 후 하차 ② 목표층·문·통과 공간 조건을 유지한 채 odom 상대 이동으로 하차하고 밖에서 정합 확인.
- 완료 기준: F1→F2, F2→F1 전환 각 5회, 하차 뒤 위치 오차 0.15 m 이하 `[제안값]`.
- 영역: SLAM.

### W12 왕복 미션 실행기 — P2

- 내용: 01 문서의 S0~S12, R1~R8 전체를 한 실행기에 넣는다. 단계별 시간 제한·재시도·실패 처리, 시작·중지·상태 인터페이스, 원커맨드 기동, 단계 시작·종료 로그와 rosbag 기록을 포함한다.
- 실패 전이(양방향 공통): 캐빈이 막힘 → 안전 위치 대기 → 다음 운행 재호출. 표시창 관측 위치에서 제한 시간 초과 → 버튼 위치로 이동 → 재호출 → 다시 관측. 하차를 놓침 → 목표층 허가 폐기 → 캐빈 대기 → 목적층 버튼 확인. 동승자의 중간층 호출·패널 가림·회전 공간 침범도 시험한다.
- 기동 순서: 최초 기동과 미션 중 Nav2 재시작을 따로 정의하고 시험한다(CR-12). 통합 프로파일에서는 검증된 유휴 팔·지게팔 노드를 허용해 지게팔 위치 기준을 지킨다.
- 가짜 장치 연동은 실물 기능이 다 되기 전에 먼저 시작해 카메라·팔·지게팔·미세 동작의 인터페이스를 고정한다.
- 기존 결함 함께 수정: CR-07(팔 명령 유실), CR-14(억제 해제 절차), CR-15(종료 시 정지), CR-20(재시도·복구), CR-21(시작 위치), CR-22(정지 확인 후 팔 동작), CR-23(실패 뒤 신호 정지), CR-25(정지 명령의 goal 취소), CR-26(미션 생존 신호), CR-28(주행 제한시간·응답 유실).
- 완료 기준: 가짜 장치·시뮬에서 정상·실패 경로 시험 통과, 현장에서 편도 1회 → 왕복 1회 → 왕복 연속 3회 `[제안값]`.
- 영역: 통합.

### W13 운영 안정성 — P0 (절차), P2 (자동화)

- 내용:
  - 미션 프로세스를 SSH와 분리해 실행한다(컨테이너 안 tmux·`docker exec -d` 등). 엘리베이터 안 Wi-Fi 단절로 SSH가 끊겨도 계속돼야 한다.
  - 자율주행 중 웹 UI를 끈다([9/12 세션 기록](../../docs/bringup_guide/2026-09-12_nav2_stutter_session_log.md): 웹 UI CPU 49% 점유). 카메라 처리 추가 뒤 CPU를 다시 측정한다.
  - DDS 설정이 Wi-Fi 인터페이스 변화에 영향을 받는지 확인한다. 9/10 공유메모리 문제 기록이 있다.
  - 시작 전 시간 동기 확인을 자동 검사로 만든다.
  - 웹 UI 재시작 시 소프트 정지 미동기화 문제가 있다. 미션 시작 전에 `/nav_safety/ready`가 true인지 확인한다.
- 완료 기준: 미션 중 SSH를 끊어도 미션 계속(현장 시험 1회). CPU 평균·최대 기록. 센서(scan·odom) 최장 공백과 배터리 여유의 합격 경계를 측정 뒤 정한다. 미션 중지·생존 신호 유실 시 주행·팔·지게팔이 모두 취소·정지되는지 시험한다.
- 영역: 통합·Docker.

### W14 하드웨어 확인 — P1

- 문턱: 보조 바퀴 H0 지상고와 탑승 재시험(9/15 절차 6절).
- LiDAR 가림: 팔 자세(home·front_view·floor_view·버튼 보기)마다 `/scan`에 팔이 잡히는지 확인한다. 잡히면 각도 필터가 필요하다.
- 팔 안전 범위: 관절별 실제 안전 PWM 범위와 자세별 충돌 여부를 잰다. 자율 미션 전 관문이다(CR-19).
- 택배·포크 외곽: 택배를 실었을 때 Nav2 footprint 밖으로 나오는지 잰다. 나오면 적재 상태 footprint를 따로 쓴다.
- 배터리: 왕복 1회 이상 버티는지 측정한다(주행·지게팔 12 V 계통, 팔 전용 배터리, Jetson).
- 버튼 형식·높이, 패널 위치, 표시창 높이, 캐빈 내부 치수를 잰다.
- 카메라 고정: 팔 끝 카메라가 진동·충격으로 각도가 바뀌지 않는지 본다.
- 영역: HW 전체.

### W15 시험 체계 — P0 (현장 기록 양식), P2 (자동 시험)

- 영역: 전체.

## 5. 진행 순서

Codex 2회차 검토 의견을 반영한 순서다.

1. 가능 여부 판정: 문턱 통과(W14), 문 열림 유지 시간(T3), 실제 버튼을 누를 수 있는지(D4), 표시창을 볼 수 있는지(W08)를 주말에 먼저 판정한다. 그 결과로 D1·D4·D5·D7·D12를 정한다.
2. 담당·기한 배정(D9).
3. 방식 결정 → 설정·보정(W01·W07·W08 교시) → 기능별 구현(W03~W11).
4. W12 가짜 장치 연동은 3과 나란히 일찍 시작한다.
5. 기능별 실물 검증(M1) → 편도(M2) → 왕복(M3) → 반복(M4). 사람·가림·이미 켜진 버튼·하차 놓침·센서 단절은 가는 길과 복귀 양쪽에서 시험한다.
6. 범용 인식·새 UI·추가 카메라는 필수 기능이 실측에서 실패할 때만 검토한다.
